01

대용량 동시 접속 성능

동시 접속 k6 부하 검증

대규모 접속이 동시에 일어나더라도 서버가 다운되지 않고 빠른 응답 속도를 유지하는 품질 조건입니다. (k6 부하 테스트 검증 완료)

02

카프카 기반 비동기 알림

Kafka 메시징 NotificationPublishEventListener

글 작성이나 결제 완료 직후 알림 전송 시 메인 서버가 멈칫거리지 않도록 알림 서버를 분리하고 카프카(Kafka)로 메시지를 전달합니다.

03

JWT 무상태 보안 인증

이중 JWT 토큰 세대 / 권한 검증

사용자 정보나 투표권 관리를 안전하게 유지하기 위해 암호화된 토큰(JWT)으로 로그인 자격과 동/호수 권한을 엄격히 검증합니다.

04

독립형 마이크로서비스 확장성

메인 API (8080) 알림 서버 (8081) Scale-out

메인 API(8080)와 알림 전용 서버(8081)를 독립적으로 나누어, 알림 이용량이 갑자기 많아져도 알림 서버만 늘려서(Scale-out) 대응합니다.

05

멀티 플랫폼 사용자 경험

Web (Next.js) Desktop (Electron / Tauri)

Web(Next.js) 환경과 Desktop(Electron/Tauri) 환경 어디서든 동일하게 빠르고 끊김 없는 반응형 인터페이스를 제공합니다.

WHY KAFKA & ASYNC NOTIFICATION
DECOUPLING · BUFFERING · FAULT-TOLERANCE

왜 Kafka를 도입했는가?
메인 업무 지연 없는 비동기 알림 아키텍처

WHY 01

메인 API 성능 분리 (Decoupling)

메인 백엔드(8080) 응답 지연 차단

알림 발송 지연이나 외부 채널(Web Push/Kakao) 통신 장애가 발생해도 메인 API 서버의 응답 속도와 DB 트랜잭션에 영향을 주지 않도록 시스템 결합도를 완전히 제거했습니다.

WHY 02

트래픽 폭주 완충 (Buffering)

대량 공지 / 관리비 메시지 버퍼링

전체 단지 공지사항이나 월별 관리비 일괄 고지 시 순간 대량 알림 트래픽이 폭주해도 Kafka Queue에 비동기 수집하여 메인 DB와 서버가 마비되는 현상을 예방합니다.

WHY 03

유실 없는 메시지 보장 (Reliability)

알림 서버(8081) Scale-out 재처리

알림 전용 서버가 다운되거나 일시 정지되더라도 Kafka 디스크 영속 큐에 메시지가 보존되어 유실 없이 자동 재처리 및 수평 확장(Scale-out)이 가능합니다.

TROUBLESHOOTING CASE STUDY 01
DOCKER CI/CD AUTOMATION

배포 자동화 과정의
Docker Dangling 이미지 누적 & 디스크 용량 문제 해결

01 · PROBLEM

서버 디스크 용량 부족

지속적 배포(CI/CD) 시 새 Docker 이미지를 pull 받을 때 기존 이미지가 삭제되지 않고 <none>:<none> Dangling 이미지로 수십 GB 이상 계속 누적되어 서버 자원 부족 위기 발생.

02 · CAUSE

Docker Tag Overwrite

동일한 태그(:latest)로 이미지 업데이트 시 이전 이미지가 삭제되는 것이 아니라 태그만 해제되어 Dangling 상태로 남아 디스크를 차지. 배포 스크립트에 자동 정리 미비.

03 · ACTION

자동 Cleanup 스크립트

CI/CD 배포 파이프라인 후속 단계에 docker image prune -f 및 docker system prune -f 명령어를 추가하여 배포 직후 잔여 이미지를 자동 삭제되도록 개선.

04 · RESULT

2.1GB 용량 확보 & 안정화

누적되던 Dangling 이미지 일괄 정리로 2.101 GB 디스크 즉시 확보. 배포가 반복되어도 서버 용량이 일정하게 유지되는 무중단 배포 안정성 확보.

ALPHATRAGEN 32
CI/CD 배포 과정에서 Docker 이미지가 태그 덮어쓰기로 인해 <none> Dangling 상태로 디스크를 점유하던 트러블슈팅 사례입니다. 배포 파이프라인에 docker image prune -f 자동 정리 명령어를 반영하여 2.1GB의 디스크 공간을 즉시 확보하고 연속 배포 안정성을 확보했습니다.
TROUBLESHOOTING CASE STUDY 02
TOOL CALLING AGENT ROUTING

AI Agent 지능형 라우팅
Tool Description 최적화 및 LLM 라우팅 정확도 향상

01 · PROBLEM

관리비 질문 시 Tool 미호출

입주민이 특정 월 관리비나 정산 내역을 문의했음에도 LLM이 DB 조회 Tool(get_maintenance_fee)을 호출하지 않고 일반 지식/환각(Hallucination) 기반 직접 답변을 생성하는 문제 발생.

❌ ROUTING FAILURE
[User] "7월 관리비 내역 알려줘"
[LLM] (Tool Call ❌)
→ DB 조회 없이 추측성 일반 답변 출력 (환각 발생)
02 · CAUSE

Tool Description 설명 부족

Tool의 함수명과 Description이 지나치게 단순·추상적이어서, LLM이 사용자 질의 의도(Intent)와 해당 Tool 호출 간의 명확한 라우팅 연관성을 판단하지 못함.

⚠️ VAGUE DESCRIPTION
@Tool("관리비를 조회합니다.")
→ 사용 목적, 파라미터 요구조건, 호출 트리거 시점이 모호하여 라우팅 실패
03 · SOLUTION

Tool Description 정밀 강화

Tool 설명에 사용 목적, 필수/선택 인자, 트리거 유저 키워드 및 Few-shot 예시를 구체화하고, System Prompt 내 Tool 라우팅 가이드라인을 명확하게 정의.

💡 ENHANCED TOOL SPEC
@Tool("특정 입주민의 월별/상세 관리비 항목, 미납금 및 정산 내역 조회 시 반드시 호출해야 하는 툴")
04 · RESULT

라우팅 정확도 향상 & 응답 신뢰성

관리비·시설 예약 등 DB 연동 질문 시 정확한 Tool Calling 라우팅 성공률 100% 달성. 환각 답변 차단 및 DB 실시간 데이터 기반 신뢰성 확보.

✅ PERFECT ROUTING RESULT
[User] "7월 관리비 내역 알려줘"
[LLM] ⚙️ Executing get_fee_details(month='07')
→ "7월 관리비 총액은 142,500원입니다." ✅
ALPHATRAGEN 33
관리비 문의 시 LLM이 DB 조회 툴을 호출하지 않고 추측성 답변을 생성하던 라우팅 문제를 해결한 트러블슈팅 사례입니다. Tool Description에 사용 목적과 호출 시점, 인자 요구조건을 정밀하게 강화함으로써 Agent의 Tool Calling 라우팅 정확도를 100%로 향상시키고 신뢰할 수 있는 DB 기반 응답을 구현했습니다.
